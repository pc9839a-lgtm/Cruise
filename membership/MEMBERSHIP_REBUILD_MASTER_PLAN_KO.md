# 멤버십 랜딩 리빌드 마스터 기획 / 작업 규칙

> 이 문서는 `membership/` 페이지 작업의 **최우선 기준 문서**다.
> 다음 작업자는 기존 코드나 임의 판단보다 이 문서를 우선한다.
> 사용자의 명시적 승인 없이 이 문서의 고정 규칙을 변경하지 않는다.

---

## 0. 작업 목적

멤버십 랜딩은 처음 보는 사람이 아래 흐름을 자연스럽게 이해해야 한다.

1. 크루즈가 어떤 여행인지 이해한다.
2. 배 안에서 숙박만 하는 것이 아니라 **식사·공연·수영·휴식 등 여행 대부분을 즐긴다**는 것을 이해한다.
3. 항구에 도착하면 **기항지에 내려 도시 관광까지 한다**는 것을 이해한다.
4. 크루즈의 이동 방식과 편의성을 이해한다.
5. 실제 여행 동선을 본다.
6. 그 다음에 가격 문제를 본다.
7. 여행사 패키지와 직접 예약의 가격 차이를 이해한다.
8. 직접 예약이 가능한지에 대한 불안을 해소한다.
9. **직접 예약과 멤버십은 서로 다른 개념**임을 이해한다.
10. 멤버십의 결제 → POINT 적립 → 크루즈 예약 사용 구조를 이해한다.
11. CLASSIC / PREMIUM을 숫자로 비교한다.
12. 가입 조건까지 확인한 뒤 스스로 선택한다.

페이지는 설명서가 아니라 **광고 랜딩**이어야 한다.

# 1. 절대 고정 영역 — 수정 금지

아래 두 영역은 사용자가 명시적으로 수정하라고 하지 않는 한 **절대 변경하지 않는다.**

- `.hero-title`
- `.hero-visual-stage`

- 히어로 문구
- 히어로 애니메이션

- CSS 변경
- 애니메이션 변경
- JS로 텍스트 덮어쓰기
- 공통 selector를 통해 간접적으로 스타일 변경

**원본 `membership/index.html`의 히어로가 기준이다.**

## 1-3. 상단 고정영역 보호 규칙

다음 작업 전에 반드시 확인한다.

- `membership-stage3-v1.js` 또는 다른 런타임 JS가 `.hero-*`, `.review-*`를 수정하면 안 된다.
- MutationObserver가 위 영역의 텍스트를 다시 덮어쓰면 안 된다.
- 공통 CSS에서 위 영역을 타깃으로 추가 override를 만들면 안 된다.
- diff에 `.hero-` 또는 `.review-` 관련 변경이 보이면 **사용자 요청이 없는 한 작업 실패로 간주하고 커밋하지 않는다.**

# 2. 작업 방식 — 한 번에 한 섹션

## 절대 규칙

**한 섹션 작업 → 중지 → 보고 → 사용자 승인 → 다음 섹션**

사용자가 `진행`, `다음`, `ㅇㅇ`이라고 하면 **다음 섹션 하나만** 작업한다.

절대 자동으로 다음 단계까지 진행하지 않는다.

### 한 번의 작업에서 금지

- 다음 섹션까지 미리 수정
- 전체 카피 동시 교체
- 전체 CSS 일괄 최적화
- 관계없는 버그까지 같이 수정
- "이것도 좋아 보인다"는 이유로 추가 작업
- 승인되지 않은 설명 / 문장 추가

# 3. 카피 작성 규칙

## 3-1. 첨언 금지

사용자가 승인한 기획 / 메시지 밖의 설명을 임의로 넣지 않는다.

특히 다음 패턴을 피한다.

- "여기서부터"
- "마지막으로"
- "비교해볼 수 있습니다"
- "준비하면 됩니다"
- "쉽게 말하면"
- "핵심은"
- "먼저 이것만"
- "기억할 건"
- "보통 여기서"
- "이런 분이라면"
- "많이 묻는"

## 3-2. 광고 카피 원칙

설명보다 다음 순서를 우선한다.

**질문 → 숫자 / 장면 → 답**

예:

- `둘이 4박 5일 400만원?`
- `1인 200만원 → 120만원`
- `둘이 약 160만원 차이`
- `월 $100 → 200P`

## 3-3. 모호한 단어 금지

가능하면 아래 단어를 메인 카피로 사용하지 않는다.

- 준비
- 활용
- 효율
- 혜택 극대화
- 비교해볼 만함
- 빠르게 / 천천히 (근거 없는 경우)

숫자와 실제 행동을 쓴다.

# SECTION 2 — 크루즈에서는 배 안에서 모든 것을 즐긴다

## 전달해야 할 단 하나의 의미

> **크루즈는 배에서 잠만 자는 여행이 아니다. 배 안에서 먹고, 자고, 놀고, 쉬고, 공연과 시설을 즐긴다. 그리고 항구에 도착하면 기항지에 내려 도시 관광까지 한다.**

이 의미에서 벗어나지 않는다.

### 반드시 보여야 할 요소

- 객실 / 숙박
- 식사 / 뷔페 / 레스토랑
- 공연 / 엔터테인먼트
- 수영장 / 라운지 / 선내시설
- **기항지 투어 / 도시 관광**

### 권장 정보 구조

메인 메시지:

`배 안에서 먹고, 자고, 놀고`

`항구에선 도시를 여행합니다`

또는 같은 의미의 더 좋은 광고 카피를 제안할 수 있으나 **구현 전 사용자 승인을 받아야 한다.**

### 중요한 수정 포인트

기존처럼 `움직이는 호텔`, `짐을 한 번만 푼다`를 SECTION 2의 메인으로 잡지 않는다.

SECTION 2의 메인은 반드시:

**배 안에서 모든 것을 한다 + 기항지 투어도 한다**

이다.

### 설명문

불필요한 장문 설명 금지.

카드 / 사진 / 짧은 단어 중심으로 표현한다.

## 답

**아니다. 항구에 도착하면 배에서 내려 도시를 여행한다.**

### 흐름

- 아침 항구 도착
- 하선
- 관광 / 맛집 / 쇼핑 / 자유여행 또는 기항지 투어
- 정해진 시간까지 배로 복귀
- 다시 출항

### 메인 개념

**낮에는 도시 여행 / 밤에는 크루즈**

구현 전 카피 승인 필요.

- 한 화면에 너무 많은 설명을 넣지 않기

## 리듬

모든 섹션을 카드로 만들지 않는다.

권장 리듬:

`큰 문장 → 사진 → 숫자 → 카드 → 큰 문장`

## 모바일

타깃 연령 30~60대.

- 작은 글씨 금지
- 과도하게 촘촘한 UI 금지
- 긴 문단 금지
- 모바일 중앙정렬을 기본으로 하되, FAQ / 조건 / 데이터 리스트는 읽기 좋은 정렬 우선

# 6. 기술 규칙

## 6-1. CSS

- 새 hotfix CSS 파일을 계속 추가하지 않는다.
- 실제 owner CSS를 수정한다.
- 같은 속성을 여러 파일에서 `!important`로 싸우게 만들지 않는다.
- 캐시 버전이 필요하면 middleware의 query version만 갱신한다.

## 6-2. JavaScript

- 기존 원본 문구를 런타임에서 광범위하게 덮어쓰는 구조를 만들지 않는다.
- 특히 `syncCoreNarrativeCopy()` 같은 함수가 **히어로 / 후기 영역을 건드리면 안 된다.**
- MutationObserver로 광범위한 DOM 텍스트를 반복 수정하지 않는다.
- 한 섹션 작업이면 그 섹션 selector만 만진다.

## 6-3. 모바일 애니메이션

- 모바일에서 GSAP / ScrollTrigger를 다시 활성화하지 않는다.
- 모바일은 CSS / WAAPI 기반을 유지한다.

## 6-4. 유지해야 하는 콘텐츠

사용자 명시적 삭제 요청 없이는 삭제 금지:

- FAQ
- 가입 조건
- POINT 설명
- 플랜 상세 정보
- 비용 구성 설명
- 가이드 설명
- 지중해 7개 일정 카드
- 160만원 활용 영역

## 6-5. 계속 제거 상태 유지

- 문의 폼은 임의로 복구하지 않는다.
- KRW / 환율 UI를 다시 넣지 않는다.
- 중간 챕터 타이틀 블록을 다시 만들지 않는다.

# 7. 매 작업 전 체크리스트

1. 사용자가 승인한 **현재 섹션 번호** 확인.
2. 해당 섹션 외 파일 / selector를 수정할 이유가 있는지 확인.
3. `membership/index.html`의 히어로 / 후기 원본과 비교.
4. 현재 대상 파일을 GitHub에서 다시 fetch.
5. owner 파일만 수정.
6. 임의 카피 / 첨언을 추가하지 않았는지 확인.
7. diff에서 `.hero-`, `.review-` 변경 여부 확인.
8. 다른 섹션 selector가 diff에 섞였는지 확인.
9. 필요할 때만 cache query 갱신.
10. 커밋.
11. **즉시 중지.**
12. 사용자에게 변경 범위만 보고하고 다음 승인 대기.
